# 轻阅 GitHub 分支、版本与功能对齐规则

参考 [api-workbench 的分支与发布约定](https://github.com/ljy-codes/api-workbench)。轻阅采用 Swift/AppKit 和 C#/WPF 两套原生实现，功能契约统一。

## main 跨端协作硬性准则

1. Windows 与 macOS 的最终用户功能和最终应用图标必须一致；功能以[功能对照表](功能对照表.md)为共同契约，图标以同一最终设计源为基准，允许按平台格式生成不同资源文件。
2. 任一端可以先行开发，并可在版本规划中为另一端预留版本号；预留版本号只表示发布协调，不代表另一端已经实现或验收。
3. 不得代写另一端实现，不得修改 `macos` 或 `windows` 分支的源码、资源、版本文件及发布记录。
4. 跨端修改必须事先取得用户明确授权。未取得授权时，只能在当前平台分支完成本端工作，不得以“对齐”为由改动另一端。
5. `main` 只维护共同契约、基线和说明，不替代任一平台分支的实现与验收。

## 版本与标签

- Mac 产品版本的次版本号使用偶数：0.4.0、0.6.0……；构建号也使用偶数：14、16……。
- Windows 后续产品版本的次版本号使用奇数：0.19.0、0.21.0……；历史 0.18.0 不重新编号。
- 新标签使用 `v<X.Y.Z>-macos` 或 `v<X.Y.Z>-windows`；本轮 Mac 标签是 `v0.4.0-macos`。
- 每个平台只保留最新 Release 和标签；旧版本经提交历史追溯。
- Windows 已完成 Markdown `<br>` 源码级对齐、全量自动回归和安装包重建，并安装到本机 `D:\Program Files\Qingyue`；仍沿用历史 0.18.0 构建 1，未创建新 Release，目标软件人工验收待完成。后续 Windows 工作先确认现状，再执行奇数版本和单最新版本规则。

## 功能对齐

两端最终应达到同一功能契约，详见[功能对照表](功能对照表.md)。新增功能必须在功能对照表中记录两端的当前实现状态与各自测试结果；允许一端先实现，但不得把目标状态、预留版本号或另一端未完成的工作标记为已实现。阅读、编辑、搜索、Markdown、图片、表格、Mermaid、工作区、阅读清单、书签、批注、恢复和导出属于共同能力。

系统菜单、快捷键、文本组件、剪贴板、文件对话框、签名和安装器允许使用平台原生实现。不能以一端的自动测试或截图代替另一端实机验收，也不能把“目标一致”写成“当前已经全部一致”。

# 轻阅 Windows 0.6.0 设计方案

## 版本定位

0.6.0 定位为“阅读体验与跨应用复制”版本。

本版本优先解决用户打开带图片 Markdown 时可能卡顿或卡死的问题，并把复制能力定义为面向 Windows 第三方接收方的通用能力。腾讯文档是验收对象之一，同时覆盖浏览器可编辑网页、Word、WPS、邮件编辑器和普通文本编辑器。

本版本不重新设计安装器，不更换 WPF/Markdown 主架构，不引入 WebView、网络图片请求或第三方运行时。已有的默认 Markdown 预览、50 万正文字符上限、外部文件刷新、阅读位置恢复、主题和安装卸载流程继续保留。

## 当前基线与问题

当前版本已经具备：

- Markdown 默认全宽预览，编辑时进入源码视图。
- 本地相对路径图片和内嵌 PNG 图片的异步读取。
- 单图、图片总字节数、解码像素数和图片数量限制。
- HTML、纯文本、RTF、XamlPackage 多格式复制。
- 复制内容中的图片使用内嵌 PNG，不依赖原 Markdown 路径。
- 50 万正文字符预览上限和外部文件更新后的视图恢复。
- 打开过程有可取消进度，阅读排版已经有后台解析和 WPF 分批构造路径。

仍存在以下需要收敛的边界：

1. `MainWindow.Reading.cs` 中保留同步 `RenderedReading.Markdown` 路径；部分切换、恢复或测试宿主可能绕过 `EnterReadingAsync`，导致图片控件和排版在 UI 线程集中创建。
2. `MarkdownPreview` 的分屏更新仍有同步 `Update` 路径，编辑后内容变化可能在防抖触发时一次性重建大量块和图片控件。
3. `MarkdownImageView.Loaded` 更接近“控件进入视觉树”，不能可靠代表用户当前可见区域。含大量图片的文档可能在首屏阶段同时启动多个图片任务。
4. 当前复制生成器已经输出 CF_HTML 结构，但实际第三方接收方的验收只覆盖了 WPF 内存粘贴和 Word；浏览器编辑区域、腾讯文档、WPS 等接收差异尚未形成回归矩阵。
5. 当前 HTML、RTF 和 XamlPackage 由不同路径生成，复杂选区、图片、表格和代码块在不同接收方的优先格式选择可能产生差异。

## 目标与非目标

### 本版本目标

- 含图片 Markdown 打开、切换、缩放和返回预览时保持窗口可响应。
- 图片读取、解码、布局准备和过期任务都可取消。
- 首屏先显示可读正文和图片占位，图片按可见区域和资源预算逐步加载。
- 第三方应用粘贴时尽量保留标题、列表、表格、代码块、引用、链接和图片。
- 复制内容不携带本地文件路径，不依赖接收方访问原 Markdown 目录。
- 全文复制、选区复制、当前段落/表格/代码块复制使用一致的内容快照。
- 窗口缩放、侧栏切换和图片完成加载后保持源文阅读位置，不跳回顶部。
- 继续支持 50 万正文字符，并降低首次打开和重复重排的峰值成本。

### 本版本不包含

- 完整 CommonMark/GFM、脚注、数学公式或所有 Mermaid 图形。
- 远程图片下载、外部资源联网或脚本执行。
- Office 文档编辑、浏览器内嵌编辑器或云端同步。
- 文件夹级全文搜索和批量替换。
- 安装器页面重做、自动更新服务、代码签名和在线发布流程。
- 改变现有用户资料格式、会话结构或原文保存格式。

## 方案比较

### 方案 A：阅读管线稳定化 + 通用剪贴板兼容（推荐）

统一所有 Markdown 阅读入口到可取消的异步管线；图片改为可见区域优先加载；复制保留现有多格式输出，但抽出统一快照和第三方接收方验证层。

优点是直接处理用户最严重的卡死风险，同时提升“读 + 复制”的核心体验，改动可以集中在现有 Windows 阅读链路。

风险是需要补充 WPF 视觉树、滚动位置和剪贴板原生格式的回归，验证工作比单独改按钮更多。

### 方案 B：先重做复制格式

先只修改 CF_HTML、RTF 和图片打包，增加浏览器、腾讯文档和 Word 的复制验收，图片打开性能继续沿用现状。

优点是范围较小，用户能快速看到复制效果。

风险是无法解决带图文档卡死；如果卡顿来自排版和图片控件构造，复制改进不能降低打开风险。

### 方案 C：引入完整 Markdown/浏览器渲染器

使用浏览器或第三方 Markdown 引擎统一预览和复制。

优点是语法覆盖和网页复制能力可能更完整。

风险是增加运行时体积、资源安全、源文位置映射、离线图片、安装包和升级复杂度，偏离轻阅当前的本地轻量定位。本版本不采用。

## 用户可见行为

### 1. 打开和阅读

打开 Markdown 后继续默认进入阅读预览。打开过程只展示简洁进度和可取消操作；不会因为图片未完成而阻塞正文显示。

用户先看到：

- 标题、段落、列表、表格和代码块；
- 图片位置的加载占位；
- 已经完成解码的图片。

图片加载失败、路径不存在、格式不支持或超过资源预算时，在对应位置显示明确说明，正文其余部分继续可读。

切换标签、关闭文档、返回编辑或再次刷新预览时，旧的图片读取和排版任务必须取消，旧任务完成后不能覆盖当前标签。

### 2. 图片加载

图片支持范围保持现有边界：本机文件、文档相对路径、合法的 `file:` 路径和受支持的内嵌 PNG。远程地址继续显示未加载说明。

加载策略调整为：

- 解析阶段只提取图片引用和显示元数据，不在 UI 线程读取文件或解码。
- 首屏及其附近区域优先加载。
- 用户滚动到其他图片区域时，再调度新的加载任务。
- 同时解码数量受限，过期任务立即取消。
- 单图、总字节数、总解码像素和控件数量继续受预算保护。
- 对相同文件在同一文档会话内复用已解码位图；缓存使用文件路径、文件长度、最后写入时间和目标解码尺寸作为身份，容量受限并可淘汰。
- 外部图片文件变化后，不复用旧位图，重新读取并更新对应图片。

图片缓存只保存解码后的内存位图，不写入用户目录，不改变原 Markdown，不跨用户资料目录持久化。

### 3. 跨应用复制

复制入口继续提供：

- 复制选区；
- 复制全文（含图片）；
- 复制当前段落；
- 复制当前表格；
- 复制当前代码块；
- 复制阅读纯文本；
- 复制原始 Markdown。

阅读内容复制使用同一个不可变快照生成多种剪贴板格式：

| 格式 | 用途 |
| --- | --- |
| `UnicodeText` / `Text` | 记事本、纯文本输入框、无富文本接收方 |
| `HTML Format` | 浏览器编辑区、腾讯文档、Word、WPS、邮件编辑器 |
| `RTF` | Office/WPS 等优先读取 RTF 的接收方 |
| `XamlPackage` | WPF 原生接收方的图片和结构兜底 |
| `Bitmap` | 选区仅包含单张图片时的图片粘贴兜底，可选 |

HTML 使用 Windows CF_HTML 的 UTF-8 字节偏移格式，片段中使用自包含 `data:image/png;base64,...` 图片。不得输出原始文件路径、UNC 路径、`file:` 地址、远程地址或可执行 HTML。

复制时先冻结源文档和选区快照，再生成格式；复制过程中如果正文、预览文档、标签或图片状态发生变化，取消本次发布并提示用户重试。复制不改变阅读选区、编辑选区、滚动位置或撤销栈。

第三方接收方验收分为两层：

1. 生成层：检查剪贴板数据中各格式的内容、CF_HTML 偏移、图片自包含性和安全白名单。
2. 接收层：在浏览器 `contenteditable` 页面、Word、WPS、腾讯文档和纯文本编辑器中实际粘贴，分别检查标题、列表、表格、代码、图片和普通文字。

接收方可以主动丢弃 HTML、图片或部分 CSS；这种情况保留纯文本兜底，并在文档中记录为接收方能力差异，不把它误判为轻阅输出失败。

### 4. 缩放、编辑和外部更新

窗口大小、侧栏显示、字号和版心变化只对现有文档做重排，不重新读取已缓存图片，不把位置重置到顶部。

位置恢复优先使用源文锚点和当前 Markdown 块，其次使用显示文档位置。图片加载完成后只更新该图片的尺寸和占位状态，不能覆盖用户随后产生的滚动或选区。

编辑 Markdown 后：

- 源码仍然是唯一保存内容；
- 返回预览时使用最新源码；
- 新预览生成期间保留旧预览或显示加载状态；
- 用户可以取消过期预览；
- 预览完成后按源文锚点恢复阅读位置。

外部文件更新继续遵守 0.5.0 的规则：无本地未保存编辑时自动接纳，有本地编辑时保留本地内容并提示冲突；刷新后的图片引用、搜索选区、目录和阅读位置使用新的源文映射。

## 技术设计

### 1. 统一 Markdown 异步管线

现有主路径：

`MainWindow → EnterReadingAsync → ReadingModel.Build → RenderedReading.MarkdownAsync → MarkdownPreview.BuildDocumentAsync → PublishReading`

0.6.0 将所有用户触发的 Markdown 阅读入口统一到这条路径：

- 首次打开；
- 从编辑返回阅读；
- 会话恢复；
- 外部文件刷新；
- 主题/字号/版心变化后的重建；
- Markdown 分屏预览更新。

`RenderedReading.Markdown` 和 `MarkdownPreview.Update` 可以保留给纯测试或离屏兼容场景，但真实窗口不再在事件处理器中同步构造含图片的完整阅读文档。

新增统一的请求状态：

```csharp
internal sealed record MarkdownRenderRequest(
    EditorTab Tab,
    string Text,
    string? SourcePath,
    double FontSize,
    double ReadingWidth,
    long Generation);
```

主窗口持有当前请求的 `CancellationTokenSource` 和生成号。发布前必须确认：

- 当前标签仍然存在并且仍为活动标签；
- 文本、路径、类型和生成号仍一致；
- 请求未取消；
- 应用未进入退出流程。

### 2. 图片调度和缓存

新增 Windows 内部组件：

- `MarkdownImageScheduler`
  - 维护当前预览中的图片视图；
  - 监听宿主滚动和尺寸变化；
  - 计算首屏及邻近区域；
  - 调度、取消和限流加载；
  - 只把不可变的 `BitmapSource` 发布回 UI。
- `MarkdownImageCache`
  - 使用有上限的进程内 LRU；
  - 键包含规范化本地路径、文件签名、内嵌目标摘要和解码尺寸；
  - 淘汰时释放位图引用，不写磁盘。
- `MarkdownImageLoadResult`
  - 区分成功、未找到、损坏、不支持、超限、取消和源文件变化；
  - 记录单图耗时和字节/像素预算结果。

现有 `MarkdownImageLoader` 继续负责安全路径解析、字节读取和 WIC 解码；把它改为可接受调度器请求和缓存命中的纯异步服务。任何文件读取、Base64 转换、图片头读取和解码都不能回到 Dispatcher。

首屏调度不依赖 `Loaded` 事件单独判断可见性。优先使用图片控件相对于阅读宿主的坐标和当前视口计算；坐标不可用时采用有限数量的顺序预加载，并在首次布局完成后重新计算。

### 3. 复制快照和格式生成

新增内部不可变模型：

```csharp
internal sealed record ReadingClipboardSnapshot(
    string PlainText,
    string Html,
    string? Rtf,
    MemoryStream? XamlPackage,
    ReadingImageReport Images);
```

实际实现可以采用等价的不可变类型，但必须保证各格式来自同一份选区和同一份图片快照。

生成流程：

1. 在 UI 线程确认当前预览、选区和图片状态。
2. 建立只读的结构化导出模型，不直接把活动 WPF 控件交给后台线程。
3. 读取已完成的冻结位图或等待有限时间；等待可取消。
4. 生成 HTML/RTF/XamlPackage/纯文本。
5. 校验总字节数、元素数、图片数、单图大小和总像素。
6. 在 UI 线程一次性发布 `DataObject`。

保持现有安全规则：

- HTML 只输出白名单标签和样式；
- 图片只接受已解码位图并重新编码为 PNG；
- 不输出 URI、路径、脚本、表单和外部 CSS；
- 超限图片保留明确占位符；
- 目标文件导出继续使用原子写入和当前原文保护。

### 4. 布局和位置恢复

增加 `ReadingViewportState`，至少包含：

- 源文顶部锚点；
- 源文块标识；
- 当前显示选区的源文起止位置；
- 视口水平/垂直偏移作为最后兜底；
- 生成号。

每次重排按以下顺序恢复：

1. 根据源文锚点找到新文档对应块；
2. 将源文位置映射到新显示文档；
3. 在布局完成回调中只执行一次恢复；
4. 若用户已产生新的滚动、选择、标签切换或编辑，则放弃旧恢复回调；
5. 最后才使用受限的垂直偏移兜底。

图片完成加载只触发局部测量和位置校正，不重建整个 FlowDocument。

### 5. 诊断

沿用现有“不记录文件名、路径、正文和图片”的诊断约束，补充以下阶段：

- Markdown 解析耗时；
- 文档块构造耗时；
- 首屏可读耗时；
- 首屏图片完成数和耗时；
- 取消耗时；
- 复制快照和各格式生成耗时；
- HTML、RTF、XamlPackage 和图片输出大小。

诊断只保留当前运行的最近记录，用户可从帮助菜单查看，不写入用户文档内容。

## 兼容性与风险控制

- 旧版会话、草稿、设置和书签继续读取。
- 图片缓存只存在进程内，不产生迁移文件。
- 外部图片变化按文件签名失效缓存，不能用旧位图覆盖新内容。
- 新异步请求必须有标签、文本和生成号三重校验，防止旧任务覆盖新标签。
- 图片调度失败只影响图片，不影响正文、搜索和复制纯文本。
- 复制富文本失败时保留纯文本复制能力，并在状态栏说明。
- 接收方丢弃图片或样式时，记录为第三方能力差异；轻阅仍提供 UnicodeText 兜底。
- 不使用无限并发、无限缓存、无限 Base64 或无上限的 FlowDocument 元素构造。
- 对用户提供的真实带图 Markdown 建立只读副本回归，不把业务正文、图片和路径提交 Git。
- 卡死问题若无法稳定复现，只能以“UI 线程不执行文件读取/解码、任务可取消、看门狗保持响应、真实样本回归通过”作为可验证修复证据，不宣称已经证明历史故障的唯一根因。

## 验收标准

### 阅读和图片

1. 打开含本地图片、内嵌图片、损坏图片、缺失图片和大量图片的 Markdown 时，正文先显示，窗口保持可操作。
2. 切换标签、关闭文档、返回编辑和刷新文件时，旧图片任务可取消，不能覆盖新文档。
3. 首屏图片优先加载，滚动后其余图片继续加载；超出预算有明确占位。
4. 图片加载完成、窗口最大化/恢复、侧栏开关和字号变化后，阅读位置和搜索高亮保持。
5. 50 万正文字符 Markdown 仍能预览；超出正文或资源预算时明确降级，不崩溃。

### 跨应用复制

1. 复制选区和全文的纯文本内容逐字正确，中文、Emoji、CRLF 和空单元格不丢失。
2. 浏览器 `contenteditable` 粘贴后保留标题层级、列表、表格、代码块、引用和图片。
3. Word、WPS 和腾讯文档粘贴后分别检查标题、表格、图片、代码块和普通段落。
4. 图片复制后不依赖原 Markdown 路径；关闭或移动原文后，已复制内容仍可粘贴。
5. 接收方只接受纯文本时，粘贴内容仍可读；接收方拒绝某种富文本格式时不影响程序稳定性。
6. 复制不改变原选区、滚动位置、编辑撤销栈和未保存状态。

### 工程质量

1. Release 构建 0 警告、0 错误。
2. 完整 Windows 回归、真实样本专项、复制格式检查和安装器回归全部通过。
3. 至少完成浏览器本地页面、Word 或 WPS、腾讯文档三类实际接收方验收；未安装的接收方明确记录为未验收。
4. 0.6.0 安装包、ZIP、文件版本、系统登记、默认保留资料卸载和彻底清理回归通过。
5. Git 工作区干净，设计、测试记录、版本变更和交付产物同步到 `feat/windows-client`。

## 实施顺序

1. 先补充带图 Markdown 的失败回归和 UI 响应看门狗，确认同步构造路径。
2. 统一真实窗口的 Markdown 异步构造和取消，确保旧任务不能发布。
3. 实现图片调度、可见区域优先、缓存和资源释放。
4. 抽取统一复制快照，验证 CF_HTML 和多格式一致性。
5. 进行浏览器、Word/WPS、腾讯文档实际粘贴验收。
6. 补齐缩放、搜索、外部更新、编辑/预览往返和 50 万字符回归。
7. 更新版本、说明、安装包并完成本机安装验证。

## 设计自检

- 方案优先处理用户报告的带图 Markdown 卡死，再处理跨应用复制兼容。
- 复制功能边界定义为第三方接收方通用能力，腾讯文档只是验收对象之一。
- 没有把现有 HTML/RTF/XamlPackage 实现全部推倒；先用接收方矩阵确认真实缺口，再做最小改动。
- 没有改变原文存储、用户资料、安装器卸载策略或 Mac 工程。
- 所有异步任务都有取消、生成号和当前标签校验。
- 图片、HTML 和复制都有大小、数量、深度、像素和耗时边界。
- 验收标准同时覆盖生成数据正确性和第三方实际粘贴效果，避免只看内部对象就宣称兼容。

# 轻阅跨平台版本与功能对齐规则

## 长期分支

| 分支 | 职责 |
| --- | --- |
| `main` | 项目基线、公共说明、功能矩阵和对齐规则 |
| `macos` | Mac 原生实现、构建与验收 |
| `windows` | Windows 原生实现、安装器与验收 |

临时分支在对应长期分支接续并核对提交后删除。Git 历史保留实现和验收追溯能力。

## 版本规则

- Mac 次版本使用偶数：`0.4.0`、`0.6.0` 等；构建号使用偶数。
- Windows 次版本使用奇数：`0.19.0`、`0.21.0` 等；历史 `0.18.0` 不重新编号。
- 标签使用 `v<X.Y.Z>-macos` 或 `v<X.Y.Z>-windows`。
- 每个平台只保留最新 Release 和标签；历史版本通过 Git 提交和验收记录追溯。
- Windows 文件版本采用四段格式，例如产品 `0.19.0`、构建 `1` 对应文件版本 `0.19.0.1`。

## 功能对齐流程

1. 以 `main` 的功能对照表确定共同功能契约。
2. 在平台分支分别实现，使用该平台原生控件、快捷键、文件系统和剪贴板能力。
3. 两端新增或修改同一能力时，同时更新源码、自动测试、使用说明和验收记录。
4. Windows 发布前执行 Release 构建和完整测试脚本，确认退出码为 0。
5. 安装最新安装包后检查版本、卸载登记、快捷方式、主窗口和核心流程。
6. 新版本验证成功后才清理旧安装包；用户数据不得作为普通构建产物删除。

## 验收门槛

功能对齐至少需要：

- 对应共同功能已有可执行代码和自动化测试。
- 菜单、快捷键或设置入口与功能矩阵一致。
- 错误、取消、超限和恢复路径有明确结果。
- 不把“目标一致”写成“当前已经全部一致”。
- 不以一端自动测试替代另一端实机验收。

## 平台差异判定

以下属于允许的平台差异：

- 系统菜单、快捷键修饰键、文件对话框、资源管理器/Finder、剪贴板格式和安装器。
- POSIX ACL/xattr 与 Windows ACL/重解析点的等价安全语义。
- AppKit/TextKit 与 WPF 的控件结构和布局实现。
- 窗口内工具条、侧栏组织方式等不改变用户能力的平台呈现。

以下不属于允许差异：

- 共同功能缺少入口、缺少真实副作用或只保留菜单占位。
- 取消后仍提交旧结果、覆盖用户正文或继续写文件。
- 资源上限、错误降级、恢复策略在两端语义不一致。
- 只通过源码分支存在判定功能完成，未验证实际 UI 行为。
